## 1. Why this exists

Typical backend JDs (Cura Label and peers) ask you to: design low-latency Rust services; write idiomatic Tokio; integrate databases, queues, and APIs; debug distributed failures; ship CI and reviews. They almost never name an ORM. They name **capabilities**.

servitor is a fake company ledger, not a tutorial CRUD app. Money movement forces you to get correctness right: balanced entries, idempotency, exactly-once-ish side effects, cache invalidation, and an audit trail.

**Jobs this unlocks:** Backend listings; backend-shaped Systems roles; any posting that mentions Tokio, Axum/Actix, Postgres, Kafka, AWS/K8s, observability, or on-call.

## 2. What you will learn

You should be able to explain each of these out loud, with a diagram, without notes.

- Tokio runtime: tasks, `JoinSet`, cancellation, `select!`, why you do not hold a `Mutex` across `.await` on a hot path
- Axum extractors, layers (auth, request-id, timeout), and how they compose with `tower`
- sqlx + Postgres: compile-time queries, migrations, transactions, isolation
- Transactional outbox: why “write DB then publish” loses messages
- At-least-once delivery + idempotent consumers (inbox / dedupe table)
- Redis as a cache, not a source of truth; explicit invalidation
- gRPC with tonic next to REST, same domain service
- OpenTelemetry traces + Prometheus histograms; what a span vs a metric is for
- Docker Compose for local prod-shaped deps; a Kubernetes Deployment you could actually apply
- Load testing and a written p99 budget
- How you would page yourself: two failure modes, symptoms, first commands

## 3. Problem statement

Build **Servitor**, a multi-tenant ledger.

A tenant (a customer of your API) has many accounts. Callers post **journal entries**: a set of lines that must sum to zero (double-entry). Posting an entry is the write path. Reading an account balance is the hot read path. After a successful post, other systems must hear about it (projections, webhooks later). You will implement that notification with a **transactional outbox** and a worker that publishes to Kafka (Redpanda in Compose) or NATS. A consumer builds a **read model** and keeps Redis in sync.

You are both the engineer and the on-call. The README is the product.

## 4. Requirements freeze

Do not start Phase 2 until this section is copied into `docs/requirements.md` in the repo and you are unwilling to add features not listed here.

### 4.1 Functional

| ID | Requirement |
| --- | --- |
| F1 | Multi-tenant isolation. Every row is scoped by `tenant_id`. A token for tenant A cannot read or write tenant B. |
| F2 | Accounts: create, get, list. Fields: id, tenant_id, name, currency (ISO-4217, start with `USD` only), created_at. |
| F3 | Journal entry post: array of lines `{account_id, amount_cents, side}` where `side` is `debit` or `credit`. Sum(debits) must equal sum(credits). At least two lines. All accounts must belong to the same tenant and share currency. |
| F4 | Entry is immutable after commit. No update/delete of posted entries. Reversals are a new entry that references `reverses_entry_id`. |
| F5 | Idempotency: `Idempotency-Key` header on POST `/v1/entries`. Same key + same tenant + same request hash returns the original entry. Different body with the same key returns `409`. |
| F6 | Balance read: `GET /v1/accounts/{id}` returns `posted_balance_cents` derived from the read model (not a full table scan of lines on every request). |
| F7 | List entries for an account with cursor pagination (`limit`, `after`). |
| F8 | REST API versioned under `/v1`. Errors are JSON `{code, message, request_id}`. |
| F9 | gRPC service `Ledger.PostEntry` and `Ledger.GetAccount` with the same invariants as REST. |
| F10 | Health: `GET /healthz` (process up). Ready: `GET /readyz` (Postgres ping + Redis ping + Kafka/NATS connectivity). |
| F11 | Auth: bearer API keys stored as hashes. Key is created via a CLI or bootstrap SQL for local use. No OAuth. |
| F12 | Outbox: inserting an entry and its outbox row is one Postgres transaction. A publisher worker drains `outbox` and writes to the log. |
| F13 | Consumer is idempotent: processed event ids live in an `inbox` table. Duplicate deliveries do not double-apply the read model. |
| F14 | Redis caches account balances. Cache key `bal:{tenant}:{account}`. Invalidate on apply. Never write Redis inside the posting transaction. |
| F15 | Structured JSON logs with `request_id`, `tenant_id`, `entry_id` where relevant. |

### 4.2 Non-functional

| ID | Requirement |
| --- | --- |
| N1 | Local Compose p99 for `GET /v1/accounts/{id}` ≤ **20 ms** at 200 rps, 1 tenant, warm cache. |
| N2 | Local Compose p99 for `POST /v1/entries` ≤ **80 ms** at 50 rps (includes commit + outbox insert, not consumer lag). |
| N3 | Consumer lag under that write load: p99 < **2 s** from commit to read-model apply. |
| N4 | Crash safety: kill `-9` the API mid-post. Either the entry exists with outbox row, or neither exists. Never entry without outbox. |
| N5 | Duplicate publisher delivery must not corrupt balances. |
| N6 | Timeouts: inbound request 5 s; DB 2 s; Redis 200 ms (then fall through to Postgres). |
| N7 | No `unwrap`/`expect` on request paths. Errors map to status codes. |
| N8 | `cargo fmt`, `clippy -D warnings`, unit + integration tests in CI. |
| N9 | Images run as non-root. Secrets from env, never committed. |
| N10 | OpenAPI 3 doc generated or handwritten and kept in sync. Proto files are source of truth for gRPC. |

### 4.3 Out of scope (do not build)

- Multi-currency FX, interest, or billing invoices
- Real webhooks, Stripe, or a frontend
- Multi-region, sharding, or Saga orchestration
- End-user signup / password reset
- Kubernetes operator or Helm chart beyond one Deployment + Service + ConfigMap
- Exactly-once Kafka transactions (you will document at-least-once + inbox)

## 6. Design (freeze before coding domain)

### 6.1 Components

```
Client ──REST/gRPC──► API
                         │  begin txn
                         │  insert entries + lines
                         │  insert outbox
                         │  commit
                         ▼
                      Postgres
                         │
              publisher worker (poll/SKIP LOCKED)
                         │
                         ▼
                    Redpanda topic `ledger.entries`
                         │
              projection consumer
                         │  upsert balances, insert inbox
                         ▼
                      Postgres read model + Redis DEL
```

### 6.2 Write schema (minimum)

- `tenants(id, name, created_at)`
- `api_keys(id, tenant_id, key_hash, prefix, created_at, revoked_at)`
- `accounts(id, tenant_id, name, currency, created_at)` unique `(tenant_id, name)`
- `entries(id, tenant_id, idempotency_key, request_hash, reverses_entry_id, created_at)` unique `(tenant_id, idempotency_key)`
- `entry_lines(id, entry_id, account_id, amount_cents, side)`
- `outbox(id, topic, payload, created_at, published_at)`
- `inbox(event_id primary key, applied_at)`
- `account_balances(account_id primary key, tenant_id, posted_cents, updated_at)`

`amount_cents` is `bigint`. Never `f64` for money.

### 6.3 Failure modes you must design for

| Failure | Expected behavior |
| --- | --- |
| API crash after commit, before HTTP response | Client retries with same Idempotency-Key; gets same entry |
| Publisher crash after Kafka ack, before `published_at` | Re-publish; consumer inbox drops duplicate |
| Publisher crash before Kafka ack | Re-publish; same as above |
| Redis down | Reads go to `account_balances`; readyz may fail or degrade — pick one and document it |
| Kafka down | Posts still succeed (outbox piles up); readyz fails; lag metric rises |
| Consumer crash mid-apply | Transaction so inbox + balance roll back together |
| Clock skew | Use DB `now()` for `created_at`, not the app clock |

### 6.4 API sketch

REST:

- `POST /v1/accounts`
- `GET /v1/accounts/{id}`
- `GET /v1/accounts?limit=&after=`
- `POST /v1/entries` + `Idempotency-Key`
- `GET /v1/entries/{id}`
- `GET /v1/accounts/{id}/entries?limit=&after=`
- `GET /healthz` `GET /readyz` `GET /metrics`

gRPC: package `servitor.ledger.v1`.

## 7. Waterfall phases

Each phase has **exit criteria**. Do not start the next phase until they are true. If you discover a requirement hole, update `docs/requirements.md` first, then code.

### Phase 0 — Project setup (2–3 days)

**Work**

- `cargo new` workspace, CI workflow (`fmt`, `clippy`, `test`)
- `compose.yaml` with Postgres, Redis, Redpanda, OTel, Prometheus
- README: how to boot deps
- Empty `docs/requirements.md` filled from section 4
- `.env.example`

**Exit**

- `docker compose up -d` works on your machine
- CI is green on an empty test
- Requirements file committed

### Phase 1 — Design freeze (2–3 days)

**Work**

- `docs/architecture.md`: diagram, schemas, failure table
- `proto/ledger.proto`
- `openapi.yaml` for REST
- Sequence diagram for post + consume
- Choose UUID strategy and idempotency hash (SHA-256 of canonical JSON)

**Exit**

- A peer (or future you) can implement the write path from the docs alone
- No new functional IDs added without striking something else

### Phase 2 — Persistence and domain (4–6 days)

**Work**

- sqlx migrations for write schema
- Domain types: `TenantId`, `AccountId`, `Money`, `Entry` with a `validate_balanced()` that is the only way to construct a postable entry
- Repository functions: create account, post entry in a transaction with outbox
- Unit tests for balance rules, tenant mismatch, currency mismatch, single-line reject

**Exit**

- `cargo test -p servitor-ledger` covers F3–F5 at the domain/repo level (API not required yet)
- A SQL integration test posts an entry and sees one outbox row in the same commit

### Phase 3 — HTTP API and auth (4–6 days)

**Work**

- Axum router, error type, request-id middleware
- API key extractor
- REST handlers for F2–F8, F10, F11
- Integration tests against Compose Postgres (testcontainers or compose)

**Exit**

- `curl` can create a key (CLI), create two accounts, post a balanced entry, fetch it
- Unbalanced post returns `422`
- Cross-tenant access returns `404` (do not leak existence) or `403` — pick one, test it
- Idempotent replay returns `200` with same body

### Phase 4 — Worker: publisher + consumer (4–6 days)

**Work**

- Publisher: `SELECT … FOR UPDATE SKIP LOCKED`, publish, mark `published_at`
- Consumer: apply to `account_balances`, insert `inbox`
- CLI `replay-outbox` for stuck rows
- Tests: duplicate event, crash between apply steps (transaction test)

**Exit**

- F12–F13 demonstrated with a test that publishes twice
- Kill publisher; restart; outbox drains
- Balance matches sum of lines after 100 posts

### Phase 5 — Redis + gRPC (3–5 days)

**Work**

- Cache-aside on GET account; invalidate in consumer after commit
- Redis timeout + fallback (N6)
- tonic server sharing the same ledger service trait as Axum
- `grpcurl` examples in README

**Exit**

- F9 works
- Cache hit / miss metrics increment
- Integration test: post → wait for consume → GET hits Redis (inspect metric or a test hook)

### Phase 6 — Observability (3–4 days)

**Work**

- OTLP traces on HTTP, sqlx, Kafka
- Prometheus: request latency histogram, post count, outbox depth, consumer lag, cache hit ratio
- Dashboard optional
- `docs/runbook.md`: two incidents (see section 9)

**Exit**

- One screenshot or saved JSON of a trace that shows HTTP → SQL → commit
- `/metrics` scrapeable
- Runbook exists

### Phase 7 — Load, packaging, k8s (3–5 days)

**Work**

- k6 script for N1–N3
- `docs/load-test.md` with hardware, command, and actual p50/p99
- `Dockerfile` multi-stage
- `deploy/k8s/deployment.yaml` + Service + probes
- Tune if you miss the budget; write what you changed

**Exit**

- N1–N3 met **or** you miss them and write a blameless note with a flamegraph/hot function and a patch. Missing the number without analysis is failure. Hitting it after one documented fix is success.

### Phase 8 — Portfolio freeze (1–2 days)

**Work**

- README: problem, architecture thumbnail, how to run, load numbers, what you would do next
- LICENSE
- Pin compose versions
- Tag `v0.1.0`

**Exit**

- Definition of done (section 9) is a checklist of green boxes

## 9. Definition of done

A hiring manager can, in 20 minutes:

1. Read the README and understand why outbox exists
2. `docker compose up` and follow a 10-line happy path
3. See `/metrics` and a trace
4. Open `docs/load-test.md` and see real numbers
5. Open `docs/runbook.md` and believe you have been on-call for this

**Runbook must include two incidents you actually induced:**

- Outbox backing up (broker down)
- Stale balance (consumer stopped) — how you detect via lag, how you recover

**Resume line is honest only if** the consumer is idempotent, the outbox is in the same transaction as the entry, and you have a measured p99.
